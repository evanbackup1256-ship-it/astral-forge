# Regression suite coverage

Run lune run REGRESSION_SUITE/run.luau from the repository root. The entry calls scripts/verify_project.luau, which enumerates the existing named verification modules.

Current audited groups:

- Crate kit metadata: `verify_crate_asset_manifest` requires a valid uploaded kit ID, exactly twenty unique skin IDs, and no standalone texture overrides until delivery has been separately verified. Studio Play texture fetching and visual review are recorded separately in `audit/evidence/CRATE_RUNTIME_20261006.md`.
- Arcade engine: verify_arcade_engine exercises fourteen score-only game kernels, including all four added games, Tower state/replay/persistence/expiry, privacy projections, save/load, action receipt/version fences, expiry and breaks. verify_casino_expansion checks quantum shifts and prevents the retired wager UI/chip state from returning. Native isolated gateway evidence is in audit/evidence/ARCADE_SERVER_STAGE_20261005.md; Studio Play interaction and the complete production request path remain unverified.
- Arcade viewports: `verify_arcade_viewports` requires an individually registered scene for every configured arcade game, unique builder functions, active-page rendering of the selected scene, reduced-motion handling, isolated viewport cleanup, rejection of unknown IDs before allocation, and scene modules no larger than 400 lines. Isolated Studio Edit mode also instantiated all fourteen builders; rendered ViewportFrame review of model quality, framing, lighting, and device layout remains separate.
- Roll proofs: verify_roll_proofs checks SHA/HMAC against independently generated fixtures and verifies deterministic streams/commitments. The player-facing full outcome verifier remains incomplete.
- Arcade migration: verify_arcade_migration checks one-time refunds for unfinished legacy stakes, duplicate calls, restored profiles and huge/malformed balances. Live rollout and failure recovery remain open.

- Renderer bug checks: verify_render_sources and verify_runtime_feedback execute actual icon/chat functions with incomplete inputs. They do not render an entire live page.
- Purchase status: verify_purchase_session and verify_premium_presentation cover state/receipt ordering and a headless React tree; native checkout and live visuals are not exercised.
- Layout guard: verify_layout_guard_engine covers temporal deferral, budget stopping, rollback and collision iteration. Real frame-time measurements and all platform layouts remain open.
- Palette contract: verify_forge_theme compares the new named palette to the captured baseline, checks immutable source colors and exercises accessibility reset/composition. Actual screenshots are still required.
- Guild document lifecycle: verify_guild_document_lifecycle is the first persistence reproduction/regression group. Its mock retry/success semantics do not substitute for a live multi-server DataStore run.
- Guild identity filtering: verify_guild_identity_filter executes the production TextService wrapper and create/rename filter guard, including censored, missing, and failed filter results. It does not substitute for live platform filtering or published-server verification.
- Rank firewall parity: verify_rank_categories checks that every configured leaderboard ID is accepted by RemoteFirewall as well as having a store, source value, and client board definition. Live OrderedDataStore access remains unverified.
- Guild community wiring: verify_guild_community_wire checks protocol and firewall action coverage, SessionGate grants, filtered-name routes, persistent community writes, cross-server messaging bounds and the guild UI entry points. It is a source-parity guard; live TextService, MessagingService and visual behavior still require Studio verification.
- Guild access policy: `verify_guild_access_math` covers legacy Open/global-cap defaults, closed recruitment, full guilds, existing-member continuity and invalid cap/mode boundaries. `verify_guild_community_wire` checks that leader settings reach the atomic GuildService membership update. Live multiplayer races, DataStore behavior and rendered UI remain open.
- Ascension Path respec: verify_ascension_path checks saved-tree migration, preservation of unrelated Domain data, bounded known-node refunds, Stardust price gates, repeated-respec scaling and preservation of unknown legacy markers. It tests the pure rules; it does not trigger the live action or validate the responsive confirmation UI.
- Expedition planning: verify_expedition_planner and verify_command_math check route affordability, committed Signals, bounded route terms, crew/reward/artifact consequences, versioned legacy snapshots and client/server/firewall wiring. They do not charge a live save or prove rendered device layouts or rollback behavior.
- Expanded ranks: verify_rank_categories checks nineteen player-board IDs against profile value projection, separate OrderedDataStores, server leaderboard routing, public roster summaries and own/server score fields, including Bazaar Deals, Events, and HiddenSecrets. verify_server_events tests one participation per player per positive-collection live event window. verify_hidden_ranks executes production milestone visibility, legacy claim counting, and Quick Find reveal filtering. These tests do not verify cloud DataStore budgets, season rollover/reset rules, live secret claim/reveal interaction, claim rewards, or rendered platform layouts.
- Bazaar listing transitions and presentation wiring: `verify_bazaar_listing_math` tests record sanitization, reservation/settlement, seller-slot release after payout, and bounded sale history; `verify_bazaar_listing_service` checks route/firewall/session wiring, saved-escrow-before-activation ordering, browse/sell/My Listings routing, server-paged history, cancellation/payout actions, and buyer confirmation. This remains incomplete evidence: real StoreAccess transactions, multiplayer purchases, delivery/recovery and rendered UI/device behavior remain open.

Legacy candidate groups for economy, guild goals, escrow, casino math, layouts, sessions and migration are indexed in BUG_AUDIT.md. Their coverage is not expanded by merely including them in this entry point. New-feature groups will be added with explicit behavior, failure cases and gaps as those implementations land.
